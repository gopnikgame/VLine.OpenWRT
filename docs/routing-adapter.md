# VPN Routing Adapter

Локальный предпросмотр маршрутизации Happ и INCY для OpenWrt с Xray и TPROXY Manager. Адаптер компилирует только объект Xray routing. TPROXY Manager по-прежнему импортирует серверы и владеет 04_outbounds.json. Реализация рассчитана на Lua 5.1. Отдельного сервиса и установки пакетов для предпросмотра не требуется. [Фрагменты TPROXY Manager v26.8.13](https://github.com/rico-x/tproxy-manager/blob/10b4cb8afdd6db9ee8ce30f0532831e2c0e2a511/docs/config-layout.md)

## Офлайн-пример

Из корня репозитория запустите один из режимов. Оба примера используют синтетические данные.

~~~sh
lua route-adapter.lua preview --source happ \
  --headers examples/headers.txt --policy examples/policy.json

lua route-adapter.lua preview --source incy \
  --headers examples/headers.txt --policy examples/policy.json \
  --profile examples/profile.json
~~~

На stdout выводится только JSON-кандидат. В stderr отображаются выбранный источник, стратегия, порядок, fallback и число записей каждого типа. При ошибке код завершения ненулевой, stdout пуст, диагностика не содержит заголовков, URL или тела профиля.

Вход — один сохранённый блок заголовков HTTP 200 или файл с отдельными строками заголовков. Режим Happ читает только routing с happ://routing/add или onadd и стандартным Base64. INCY читает только autorouting с add или onadd и точным HTTPS URL из локальной политики. --profile принимает заранее сохранённый JSON. Ошибка выбранного источника прерывает операцию. [Happ](https://raw.githubusercontent.com/HappDev/happ_su/main/dev-docs/routing.md), [INCY Autorouting](https://docs.incy.cc/en/autorouting/#http-header)

INCY --fetch вызывается явно на POSIX/OpenWrt. В incySource задаются точный URL и ipv4, публичный адрес проверенного источника. Curl проверяет TLS по имени из URL, использует заданный IP, отключает прокси и редиректы и ограничивает время и объём ответа. Поддерживается HTTPS на стандартном порту с простым путём без query, fragment и относительных сегментов. Политика примера не содержит IP для сетевого режима. [Параметры curl](https://curl.se/docs/manpage.html)

## Локальная политика

- inboundTag — заранее известный тег входа лабораторного LAN. Настройка nftables и проверка реального охвата остаются отдельными шагами.
- routeOrder — явно утверждённое значение block-proxy-direct. Если профиль содержит RouteOrder, он должен совпасть. Это порядок адаптера. Поведение мобильных клиентов при пересечениях зависит от их реализации.
- allowedRegex — необязательный список точных значений regexp:…. Остальные доменные правила используют full: или domain:. Поддерживаются IPv4/IPv6 и CIDR. Широкие CIDR /0, строки без префикса доменного правила и внешние ext: отклоняются.
- geo — необязательная пара geoip и geosite. Каждая запись содержит sha256 и массив categories. CLI сверяет геоправила по локальному списку. В LuCI разрешённая пара из импортированного профиля загружается при сохранении. [Работа с DAT в LuCI](../luci/README.md#правила-трафика)
- incySource — объект с url и необязательным ipv4. Для --fetch нужны оба поля.

Профиль требует строкового GlobalProxy со значением true, стратегии AsIs или IPIfNonMatch и хотя бы одного правила. DNS и вспомогательные метаданные профиля не попадают в Xray. Включённый FakeDNS, неизвестные поля и полный Xray JSON отклоняются.

Правила domain и ip для одного действия генерируются отдельно. При IPIfNonMatch первый подходящий маршрут побеждает в каждом проходе. С исходным IP правило может совпасть уже в первом проходе. Без совпадения Xray делает второй проход с DNS, затем использует первый outbound. Проверка требует, чтобы это был proxy с протоколом vless. При AsIs вместо этого добавляется завершающее правило только для выбранного inbound. [Правила Xray](https://xtls.github.io/en/config/routing.html#ruleobject), [маршрутизатор Xray 26.10.31](https://github.com/XTLS/Xray-core/blob/v26.10.31/app/router/router.go#L188-L218)

## Проверка полного теневого конфига

Для офлайн-проверки приготовьте два закрытых временных каталога с одинаковыми фрагментами штатного конфига. Для первого применения исходный набор должен быть без объекта routing. Для обновления проверьте, что прежний файл адаптера — единственный источник routing, и передайте его отдельной копией через --previous. Xray заменяет весь объект routing при загрузке следующего фрагмента. [Слияние в Xray](https://github.com/XTLS/Xray-core/blob/v26.10.31/infra/conf/xray.go#L468-L478)

Сохраните результат preview в новом файле 05-routing.json только внутри теневой копии. Перенаправление stdout в существующий файл сразу обнуляет его, поэтому для каждого прогона нужен отдельный временный каталог. Дампы Xray могут содержать учётные данные. Ограничьте права на каталоги и направьте журналы тестового Xray в приватные файлы либо задайте log.access и log.error как none в обеих временных копиях. Для проверки выберите тот же бинарник, параметры и каталог DAT, которые будут использоваться при запуске.

~~~sh
umask 077
xray run -dump -format json -confdir "$before" > "$work/before.dump" &&
xray run -test -format json -confdir "$stage" > "$work/xray-test.log" 2>&1 &&
xray run -dump -format json -confdir "$stage" > "$work/stage.dump" &&
lua route-adapter.lua verify --source happ \
  --headers "$headers" --policy "$policy" \
  --baseline "$work/before.dump" --merged "$work/stage.dump"
~~~

Если используются DAT, до -test укажите XRAY_LOCATION_ASSET на проверенный закрытый каталог с обоими файлами и убедитесь, что его не переопределяет xray.location.asset. Снимите свежие контрольные суммы в том же каталоге командой sha256sum geoip.dat geosite.dat и передайте вывод через --dat-sha256. Команда verify сравнивает этот список с локальной политикой. Доступность категорий в самих файлах проверяет Xray -test. Сравнение не заменяет проверку DNS-пути, фактического egress и сохранения первого outbound после смены сервера.

После согласованной проверки отдельно сохраняют прежний файл вне confdir, сверяют хеш кандидата и исходного набора, исключают одновременную запись менеджера и заменяют один файл через rename на той же файловой системе. Для отката так же возвращают предыдущий проверенный файл. Прототип поддерживает только preview и verify.

## Тесты

~~~sh
node --test tests/*.test.cjs
LUA_BIN=/path/to/lua XRAY_BIN=/path/to/xray node --test tests/*.test.cjs
~~~

Тесты на Node.js используют временные каталоги и синтетические профили. С XRAY_BIN проверяется штатная загрузка полного набора и сравнение его реального -dump. Для двух дополнительных SOCKS-проверок на loopback установите XRAY_LOOPBACK=1. Сетевой путь INCY в тестах моделируется через ответ curl.

[VPN Routing для LuCI](../luci/README.md) использует тот же компилятор для предпросмотра и сохранения правил. Приложение проверяет кандидат Xray до записи и применяет правила при следующем подключении только к LAN-входу VPN Routing.
